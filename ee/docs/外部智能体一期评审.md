## P0-B：方案未点破的现存漏洞（建议独立于 Phase 1 优先修）

### `POST /{agent_id}/chat` 缺会话归属校验（IDOR）

**现状**：`session_id` 直接取自请求体（`app/api/external_agents.py:337`），随后 `get_messages(session_id)`（`external_agent_chat_service.py:63`）**只按 session_id 过滤，不校验 `user_id`，也不校验 `org_id`**。

**后果**：知道他人 session UUID 的用户可以

1. 将他人对话历史作为上下文送入外部 agent（再诱导 agent 复述即可读出内容）；
2. 将自己的消息经 `_persist_messages` 写入他人会话。

**判定为遗漏而非设计**：同文件的 `GET /sessions/{id}/messages`（:286）**有**校验，走 `get_session(session_id, user_id)`，唯独 chat 端点漏了。

**修订建议**：方案军规 A 第 3 条已正确要求该校验，但归类为"Phase 1 新规则"，低估了严重性。建议在文档中单列为"存量缺陷修复"，且不与 Phase 1 排期绑定。

### 两个次要项

- 前端 4 条外部 Agent 路由（`router/index.ts:161-185`）均无 `requiredOrgRole` meta，仅靠组件内 `v-if` 隐藏按钮。后端有校验故不可利用，但与兄弟路由（:153、:159）不一致。
- `services/externalAgents.ts:53` 的 protocol 类型联合缺 `nap`（模板有、后端支持），新增 `rag_standard` 时会一并撞上。

## P1：会在实施时卡住的设计缺口

| # | 位置 | 问题 | 修订建议 |
|---|---|---|---|
| 1 | §9.2 | **自相矛盾**：称"普通用户 invoke 请求不得由后端代理发起"，但 §6.2 第 4 步明写"代理调用（httpx）"——tool 型设计本身就是后端代理 | 删除该句。真实威胁模型是**管理员配置的 URL**，防护点为"提交时校验 + org 级网段白名单"（原文后半句正确） |
| 2 | §4 manifest | `auth.type: api_key_header` 只定义 `{type, token}`，**缺 header 名字段**，无法实现 | 补 `header_name`，如 `{"type":"api_key_header","header_name":"X-API-Key","token":"..."}` |
| 3 | §4 manifest | `ui: "daterange"` 映射 `type: "string"`，**序列化格式未定义** | 定死格式（建议 `{"start":"ISO","end":"ISO"}` 或 `"起/止"`二选一并写入规范） |
| 4 | §4 / §7.2 | `output_hint: {display, primary_key}` **定位不到表格数据**。外部常返回 `{data:[...], total:N}`，前端不知数组在哪层 | 增加 `items_path`（如 `"data"`），支持点号路径 |

| 8 | §6.2 第 1 步 | 上游不可达返回 4xx，语义不当 | 改 503 |

## P2：项目规范缺失

1. **完全未提 i18n**。CLAUDE.md 强制要求 portal + 后端（`code`+`error_code`+`message_key`+`message`）。
   补充说明：现存 3 个 External Agent 视图**零 i18n**（`useI18n`/`$t` 计数均为 0，全硬编码中文）。新增向导、动态表单、字段级 422 错误若继续硬编码将放大该债务。**至少新增代码须合规**。
2. **未说明 CE/EE 归属**。`features.yaml` 中无 external_agent 条目 → 当前为 CE。此类企业集成能力是否需 `FeatureGate` 门控，需明确决策。
3. **任务分解无测试任务**。仓库有 pytest，新增协议适配器、manifest 校验、invoke 代理均属应有单测的范围。
4. `icon_emoji` 与 CLAUDE.md「禁止 emoji，图标用 `lucide-vue-next`」存在张力（作为用户选择的数据字段尚可，但建议在文档中说明豁免理由）。

## 七、可插拔性评估（追加约束：不影响其他功能、可随时插拔）

### 结论

**当前方案不满足该约束。** 方案选择在现有 `external_agents` 表 / router / 列表页上原地扩展，存在 3 处硬耦合和 1 处对现有功能的行为变更。

### 7.1 先区分：方案里两类内容的可插拔性根本不同

| | A. `rag_standard` 协议 | B. tool 型插件 |
|---|---|---|
| 本质 | 给现有 chat 型加一个协议分支 | 全新能力域 |
| 落点 | `external_agent_adapter.py` 现有 `if/elif` 分发 | 新表 + 新端点 + 新前端页 |
| 能否独立摘除 | **不能**（chat 型复用的就是这条链路） | **完全可以** |
| 可达成的保证 | 零影响增量：不加分支则现有 3 个协议行为不变 | 真正可插拔 |

方案把两者混在一起论述，导致 B 类也被设计成了不可摘除的形态。**建议在文档中显式拆开。**

### 7.2 当前方案的 3 处硬耦合 + 1 处行为变更

| 方案做法 | 问题 |
|---|---|
| §5 在 `external_agents` 表加 6 个字段 | 回滚需 drop column；已写入数据会丢失 |
| §6 新端点挂进 `app/api/external_agents.py` 同一 router | 无法单独下线；改动波及现有 11 个端点 |
| §7.2 tool 型混进现有 `ExternalAgentList` | 前端同样摘不干净 |
| **§5+§10 `status` 状态机** | **行为变更**：`draft/active/disabled` 会对**现有 chat 型 Agent 一并生效**，而它们当前没有 status 概念（建好即可用）。这已经违反"不影响其他功能" |

注：若按 7.4 建议 B 类独立建表，`status` 只存在于新表，该行为变更问题自动消失。

### 7.3 平台现有开关机制的实际能力（核查结果）

| 机制 | 粒度 | 生效时机 | 可用性 |
|---|---|---|---|
| `feature_gate.is_enabled` / `require_feature`<br>（`app/core/feature_gate.py:83`、`app/core/deps.py:432`） | 整个部署（CE vs EE） | **进程启动时**（读 `NODESKCLAW_EDITION` 或 `ee/` 目录是否存在），模块单例缓存，无 reload | ✅ 可用，但只能做 CE/EE 二分，**不是开关** |
| `OrganizationFeatureOverride` + `is_enabled_for_org`<br>（`app/core/feature_gate.py:103`） | **按组织、按功能** | 真运行时（每次请求读 DB，无需重启） | ⚠️ **基建齐全但未接线**：模型、解析函数、EE 超管 API 与 UI 都在，但 `is_enabled_for_org` **零调用点**，`require_feature` 仍只调 `is_enabled`。超管现在写 override 行**不产生任何效果** |
| 前端 `meta.requireFeature` 路由守卫<br>（`router/index.ts:271-277`） | 按功能 | 运行时（`systemInfo` 每次页面加载拉一次） | ✅ 已在 `llm_analytics`、`multi_org` 上实际使用<br>⚠️ 但 `useFeature.ts:10` 在 EE 下短路返回 `true`，需一并修 |
| `router.py` 条件注册 | — | — | ❌ **无先例**，`router.py` 100% 无条件注册。同类模式仅存在于 `main.py:945-988`（EE 模块 try/except ImportError）和 `ee/backend/router.py:37` 的 `_try_include` |

**关键发现**：已有两份设计/实施文档 `ee/docs/2026-08-10-org-feature-toggle-coverage-design.md` 与 `2026-08-11-…-plan.md` 规划了把上述 org 级开关接线，**且其中已把 `external_agent` 列入待注册的 6 个 feature**。但 git 历史显示**只有文档提交、零实现提交**，计划内所有勾选项仍为未完成。

### 7.4 建议：分两层达成

**Level 1 — 代码/部署隔离（必做，成本低，独立可交付）**

B 类 tool 插件完全独立成模块，**不碰 `external_agents` 任何现有资产**：

- 数据：新建表（如 `agent_plugins`），不扩展 `external_agents`
- 后端：新建 `app/api/agent_plugins.py`，独立前缀 `/api/v1/agent-plugins`
- 前端：独立路由 + 独立列表页，不混入 `ExternalAgentList`
- 摘除方式：注释 `router.py` 一行 `include_router` + `alembic downgrade`（drop table，无数据交叉）

达成效果：对现有 chat 型功能**零影响**，回滚干净。同时自动消解 7.2 的 `status` 行为变更问题。

**Level 2 — 运行时开关（若"随时插拔"须运行时生效，则需前置排期）**

- 前置依赖：先完成 `2026-08-11` 计划的 Task 1 —— 让 `require_feature` 改调 `is_enabled_for_org`，使 override 真正生效
- 然后：在 `features.yaml` 注册 `agent_plugin`，新 router 整体挂 `dependencies=[Depends(require_feature("agent_plugin"))]`
- 前端：新路由加 `meta.requireFeature`，导航入口 `v-if`；需同时修 `useFeature.ts:10` 的 EE 短路
- 效果：超管可按组织实时开关，无需重启

**不建议的做法**：用 `features.yaml` 的 EE 门控当插拔开关。它是 CE/EE 二分且进程启动时固化，改了要重启，语义也不对（会让该能力变成 EE 专属）。

### 7.5 A 类（`rag_standard`）的零影响保证

无法做成可插拔，但可通过约束把风险降到最低：

1. 仅在 `chat_stream` / `verify_connection` 的分发处**新增分支**，不修改 `openai_compatible` / `nap` / `custom` 任何现有分支代码；
2. 补现有 3 个协议的回归测试作为改动前置；
3. 验收标准增加一条：**现有 chat 型 Agent 行为无变化**。
