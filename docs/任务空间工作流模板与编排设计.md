## 一、产品定位

### 核心理念

```
验证（任务实验室）          沉淀（保存模板）        复用（协作空间/实验室）
┌────────────────┐    ┌──────────────┐    ┌────────────────────┐
│ 提交→拆解→确认  │    │ 验收通过后    │    │ 选模板→填需求      │
│ →执行→验收通过✓ │──▶│ "保存为工作流"│──▶│ →自动创建 Mission  │
│                │    │ （DAG 快照）  │    │ →确认/直接执行     │
└────────────────┘    └──────────────┘    │ →产物回到空间       │
                                          └────────────────────┘
```

- **任务实验室** = 试验场（验证编排逻辑是否可行）
- **协作空间** = 生产线（日常使用，聊天直接触发）
- **工作流模板** = 从试验场到生产线的桥梁（验证过的编排可复现）

### 与协作空间的关系

| | 协作空间（现有） | 任务实验室 | 工作流模板 |
|---|---|---|---|
| 定位 | 团队协作 | 任务验证 | 可复用编排 |
| 交互 | @员工对话 | 提交需求→确认 | 选模板→一键执行 |
| AI 角色 | 被动响应 | 主动拆解分派 | 按预定义 DAG 分派 |
| 结果 | 即时回复 | 产物 + 验收 | 产物（可复现） |

### 三种使用模式

| 模式 | 触发方式 | 执行方式 |
|---|---|---|
| @单聊 | @某员工 | 1:1 对话（现有能力） |
| 直接聊（编排者） | 不@任何人 | 编排者判断→对话转给合适员工 / 任务则拆解分派 |
| 方法调用 | 选工作流模板 / 聊天中匹配模板 | 按已验证的 DAG 执行，结果可复现 |

## 二、工作流模板

### 2.1 数据模型

**新表 `mission_templates`**（仿 `instance_template.py` 主表+明细表模式）：

```python
class MissionTemplate(BaseModel):
    org_id: str(36) FK organizations.id, index
    workspace_id: str(36) | None        # 空=组织级共享
    name: str(200), not null
    description: Text
    brief_template: JSONB               # {goal, constraints, acceptance_criteria, key_decisions}
    escalation_policy: JSONB            # L2 规则
    mission_type: str(16)               # standard / lightweight
    execution_mode: str(16)             # auto / step_review（快照时的模式）
    created_from_mission_id: str(36)    # 溯源 Mission
    usage_count: int, default 0
    status: str(16), default "active"   # active / deprecated
    created_by: str(36) FK users.id

class MissionTemplateNode(BaseModel):
    template_id: str(36) FK mission_templates.id, index
    seq: int, not null
    title: str(200), not null
    description: Text
    acceptance_criteria: Text
    capability_tags: JSONB              # string[]
    depends_on: JSONB                   # int[] 引用 seq
```

索引：`(template_id, seq)` 唯一 WHERE deleted_at IS NULL。

### 2.2 保存时机与流程

**时机**：`accept_mission` 事务内（验收通过 = 图被认可，节点全部 done、依赖定稿）。

**API 端点**：

| 端点 | 说明 |
|---|---|
| `POST /missions/{mid}/save-as-template` | body `{name, description}`；仅 acceptance/archived 状态；发起人或 admin |
| `GET /workspaces/{wid}/mission-templates` | 模板列表（空间级 + 组织级，active） |
| `POST /mission-templates/{tid}/run` | body `{requirement_text, execution_mode?}`；从模板实例化 Mission |
| `DELETE /mission-templates/{tid}` | 软删除 |

**实现挂载**：`accept_mission` 的 rowcount 校验后、commit 前，同事务插入模板快照（验收成功 = 模板必存）。

### 2.3 实例化流程

```python
async def instantiate_from_template(db, template, *, org, user, workspace_id, requirement_text):
    """从模板创建 Mission：直接按模板 nodes 建节点，跳过 LLM 拆解"""
    # 1. 复用 create_mission 建 draft Mission
    # 2. 按 template.nodes 逐个建 MissionNode（session_key 同 run_decomposition 格式）
    # 3. status = awaiting_confirm（用户走现有 confirm 确认后执行）
    # 4. usage_count += 1
```

**关键设计**：实例化后停在 `awaiting_confirm`，用户可微调（confirm API 支持 node_edits），确认后进 executing。后续 confirm/调度/执行链路**零改动**。

### 2.4 模板复用时的差异

| 环节 | 首次（验证） | 复用（模板） |
|---|---|---|
| DAG 确认 | 人工确认 | 仍需确认（可微调） |
| 拆解 | LLM 拆解 | **不调 LLM**（用快照） |
| 匹配 | 按 capability_tags | **重新匹配**（花名册可能变） |
| 执行模式 | 用户选择 | 模板快照（可覆盖） |
| 进度可见 | 任务实验室 | 空间 SSE + 任务实验室 |

## 三、执行模式选择

### 3.1 两种模式

| 模式 | 行为 | 适用场景 |
|---|---|---|
| **auto**（自动执行） | 确认后全部节点依次自动完成 | 已验证过的工作流、简单任务 |
| **step_review**（逐节点审核） | 每个节点完成后暂停，人工审核结果后继续 | 首次执行、高风险任务、质量把关 |

### 3.2 数据模型

Mission 新增两列：

```python
execution_mode: str(16) = "auto"      # auto / step_review
paused_for_review: bool = False       # step_review 下节点完成后置 True
```

### 3.3 调度器改动

```python
# scheduler._dispatch_due 入口处：
if mission.execution_mode == "step_review" and mission.paused_for_review:
    continue  # 跳过派发，等人工审核

# ingest_service._on_done 末尾：
if mission.execution_mode == "step_review":
    mission.paused_for_review = True
    append_event("node_review_pending",
                 content=f"节点「{node.title}」完成，请审核后继续")
```

### 3.4 审核操作

**新 API**：`POST /missions/{mid}/review-continue`

| 参数 | 行为 |
|---|---|
| `{action: "approve"}` | `paused_for_review = False` → 下游自动派发 |
| `{action: "reject", node_id: "..."}` | 该节点回 pending（attempt 重置）→ 重新匹配执行 |
| `{action: "pause"}` | 保持暂停（用户稍后回来） |

### 3.5 前端交互

任务确认页/任务卡片增加模式开关：

```
┌── 任务确认 ──────────────────────────────┐
│  ① 搜集资料 → 员工A                      │
│  ② 整理分析 → 员工B（依赖①）              │
│  ③ 撰写报告 → 员工C（依赖②）              │
│                                          │
│  执行模式：                               │
│  ● 自动执行    ○ 逐节点审核               │
│                                          │
│  [确认执行]  [取消]                       │
└──────────────────────────────────────────┘
```

逐节点审核模式下，每个节点完成后聊天流/时间线显示审核卡片：

```
┌── 节点① 搜集资料 ── 员工A ── ✓ 已完成 ──┐
│  执行总结：已读取三份文件...               │
│  产物：资料清单.md                        │
│                                          │
│  [✓ 审核通过，继续] [✗ 打回重做] [⏸ 暂停]  │
└──────────────────────────────────────────┘
```

### 3.6 与模板结合

保存模板时快照 `execution_mode`。复用时：
- 默认用模板的模式
- 用户可在触发时覆盖（验证时 step_review → 保存时切 auto → 日常一键跑完）

## 四、聊天触发编排

### 4.1 核心逻辑

协作空间中用户发消息**不 @任何人**时，编排者接管：

```python
# 伪代码：space chat 的 no_mention 分支
async def handle_unmentioned_message(workspace_id, text, user):
    intent = await classify_intent(text)  # LLM 分类："对话" or "任务"
    if intent == "对话":
        agent = await find_best_agent(workspace_id, text)
        return route_to_agent(agent, text)
    else:
        # 优先匹配工作流模板（不调 LLM，省钱且可复现）
        template = await find_matching_template(workspace_id, text)
        if template:
            mission = await instantiate_from_template(template, text)
        else:
            mission = await create_and_decompose(text, workspace_id)
        # 回复任务确认卡片到聊天流
        return send_confirmation_card(mission, workspace_id)
```

### 4.2 意图分类

| 判断 | 判断依据 | 处理 |
|---|---|---|
| 对话 | 疑问句、闲聊、快速查询 | 转给能力最匹配的员工直接回答 |
| 任务 | 有明确目标、多步骤、需要交付物 | 走编排（拆解或模板） |

**成本控制**：先查模板匹配（关键词/嵌入相似度，不调 LLM），命中则跳过分类直接用模板。未命中才调 LLM 分类 + 拆解。

### 4.3 聊天流中的卡片渲染

现有 workspace 消息是纯文本。新增消息类型：

| 类型 | 渲染 |
|---|---|
| `mission_card` | 任务确认卡片（节点列表 + 确认/取消按钮 + 执行模式开关） |
| `mission_progress` | 进度卡片（节点状态实时更新，可折叠） |
| `artifact_delivery` | 产物投递卡片（名称 + 下载/预览按钮） |
| `review_pending` | 审核卡片（节点结果 + 通过/打回/暂停按钮） |

**折叠行为**：多任务并发时，卡片默认折叠为一行摘要，点击展开：

```
┌── 🧑张三 的任务 ── 竞品分析 ── 2/3 进行中 ── [展开] ──┐
└────────────────────────────────────────────────────────┘
```

### 4.4 编排者的可见性

编排者不是 AI 员工实例，是后端服务。在聊天流中以系统身份出现：

- 头像：专用图标（齿轮/编排器标识）
- 名称：显示为"编排者"或"任务助手"
- 消息类型标注：`[任务]` / `[路由]` 区别于普通员工回复

### 4.5 产物回流

任务完成后产物推送到协作空间：

```python
# broadcast_event 推送到空间 SSE
broadcast_event(mission.workspace_id, "mission:artifact", {
    "mission_id": mid, "name": "报告.md",
    "download_url": presigned_url, "requested_by": user_name,
})
```

前端在 SSE 事件分支中渲染产物投递卡片。

## 五、多人使用支持

### 5.1 架构现状（已支持）

| 能力 | 现状 |
|---|---|
| 多人加入空间 | ✅ WorkspaceMember |
| 并发任务执行 | ✅ 调度器天然并发 |
| 同员工排队 | ✅ D9 串行 + 优先级插队 |
| 任务可见性 | ✅ 空间内全员可见 |
| 验收权限 | ✅ 发起人或 admin |

### 5.2 需补的优化

| 优化 | 解决什么 | 实现 |
|---|---|---|
| **审核人列表** | 发起人不在时无人审核 | Mission 加 `reviewer_ids: JSONB`，列表内任何人可审核 |
| **任务卡片显示发起人** | 聊天流中任务归属不清 | 卡片头部显示 `🧑发起人 的任务` |
| **折叠卡片** | 多任务并发时聊天流噪音 | 卡片默认折叠，点击展开 |
| **并发上限** | 任务洪泛占满所有员工 | MissionOrgConfig 加 `max_concurrent_missions: int`，调度器检查 |
| **通知过滤** | 用户只想看自己的任务 | 前端聊天流加"只看我的任务"筛选 |

## 九、上下文防爆机制

多节点任务架构上已防护（每节点独立 session_key + 结论文 500 字截断），但**单节点内部**的 Agent 工具调用循环和大文件读取可能撑爆上下文窗口（实测约 15 万 token 时网关报 `Context overflow`）。

### 9.1 节点级工具调用上限

| 项 | 设计 |
|---|---|
| 触发条件 | 单节点的 `tool_trace` 事件数超过 50 次 |
| 行为 | 调度器看护检测到后自动暂停节点 → L2 提示"节点工具调用次数异常，可能存在死循环，请人工检查" |
| 实现 | `scheduler._watchdog` 中新增检查：查节点 tool_trace 事件计数（已有 event_type=`tool_trace`），超限置 `blocked_question` |
| 目的 | 防 Agent 循环刷上下文 / 防 skill 内 while 死循环 |

### 9.2 文件读取截断

| 项 | 设计 |
|---|---|
| 触发条件 | skill 的 `read` 工具返回内容超过 max_chars |
| 行为 | 截断返回前 N 字符 + 文件元信息（文件名/大小/类型），尾部附"[内容已截断，如需完整内容请分段读取]" |
| 实现 | channel 插件 `tools.ts` 的文件读取逻辑加 `max_chars` 参数（默认 10000 字符）；插件侧对 read 工具的返回内容做截断 |
| 目的 | 防大文件（PDF 转文本、代码文件）一次撑爆上下文 |

### 9.3 启用 OpenClaw 引擎压缩

| 项 | 设计 |
|---|---|
| 背景 | OpenClaw 引擎内置 Compaction 体系（代码确认存在），但因 compaction hook 未启用而不会自动触发 |
| 做法 | 在实例配置（`openclaw.json` 或引擎环境变量）中启用 compaction hook；模型目录已有 `contextWindow: 204800` |
| 效果 | 接近窗口上限时自动将历史消息摘要压缩，替代硬报错 |
| 实现 | `llm_config_service.py` 的配置生成逻辑中，在 agent 配置段加 compaction 启用标记；存量实例需重启生效 |
| 依赖 | OpenClaw 引擎的 compaction hook 具体配置名需查引擎文档确认 |

### 9.4 防护矩阵

| 风险 | 防护 | 触发时机 |
|---|---|---|
| Agent 工具调用死循环 | 9.1 工具调用上限 | tool_trace > 50 次 |
| 大文件读取撑爆 | 9.2 文件截断 | read 返回 > 10000 字符 |
| 长任务自然累积到上限 | 9.3 引擎压缩 | 上下文接近窗口上限 |
| 成本失控 | P2 token 保险丝 | 消耗超阈值 |
| 单节点质量问题 | P2 step_review | 每节点完成后人工审核 |
