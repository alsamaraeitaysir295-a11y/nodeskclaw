## 二、问题清单

### P1（高）榜单范围包含全部 personal 基因，存在跨组织信息暴露

**位置**：`app/services/gene_market_stat_service.py` `_ranking()` 与 `_total()` 的范围条件

**现状代码**：

```python
or_(
    Gene.visibility == "public",
    Gene.org_id == org_id,
    Gene.visibility == "personal",   # ← 无任何归属约束
)
```

**问题**：personal 分支没有 org / owner 过滤，导致：

1. **跨租户泄露**：B 组织的统计页能看到 A 组织用户私有技能的名称与计数（事件过滤基于 Gene 的可见性，与事件的 org_id 无关）
2. **组织内隐私模型不一致**：市场列表中 personal 基因仅 owner 本人可见（`gene_service.py` list_genes 的 `visibility == "personal"` 分支带 `created_by == user_id`），但榜单对全组织乃至全平台曝光

**与方案口径的偏差**：方案明确"数据范围 = 公共市场（visibility='public'）+ 本组织"，代码额外放开了 personal。

**为什么代码会加 personal（动机成立）**：fork 到个人库产生的 personal 副本上的 install / skill_use 事件，需要按 slug 并入同一技能的计数（榜单按 slug 聚合）。一刀切排除 personal 会丢这部分事件。

**修复建议**：personal 分支仅纳入"slug 在公共/本组织可见范围存在对应副本"的行，纯私有技能不进榜：

```python
personal_branch = and_(
    Gene.visibility == "personal",
    Gene.slug.in_(
        select(Gene.slug).where(
            not_deleted(Gene),
            or_(Gene.visibility == "public", Gene.org_id == org_id),
        )
    ),
)
# 范围条件改为 or_(public, org_id==org_id, personal_branch)
```

按 slug 关联与榜单现有的 group by slug 口径一致；如需更精确也可用血缘分组 key（lineage key，三向副本共享），但注意榜单聚合本身按 slug，两者保持一致即可。

**处理时机**：多组织环境上线前必须修复。

### P2（中）"gene 删除后榜单仍可显示"的设计意图与实现相反

**位置**：`app/models/gene_market_event.py` 模型注释、方案 §1 vs `_ranking()/_total()` 实现

**矛盾**：

- model 注释与方案均称 `gene_slug/gene_name` 反范式冗余是为了"gene 被删除后榜单仍可展示名称""gene 删除不级联本表（保留历史统计）"
- 实现中 ranking 与 totals 都 `JOIN genes` 且过滤 `not_deleted(Gene)`——**软删除的技能会直接从榜单消失**，反范式字段在榜单路径上永远用不到

**修复方向（二选一，需产品拍板）**：

1. 接受"删除即出榜"：保留现实现，修正 model 注释与方案文档的表述（冗余字段仅用于审计留痕 / 榜单以外的展示）
2. 真要保留历史展示：聚合改为不依赖 genes 活性，直接用事件表冗余的 `gene_slug/gene_name` 分组（范围过滤仍需基因维度信息时可用事件表上的 org_id 辅助）

**风险**：现状是注释与行为相反，后续维护者会据注释做出错误假设。

### P3（中）month/week 窗口存在最多 8 小时的边界偏移

**位置**：`gene_market_stat_service.py` `_cutoff_for()`

**机制**：

- cutoff 用 naive `datetime.now()`（后端容器 TZ=Asia/Shanghai 的墙钟时间）
- 事件表 `created_at` 为 `timestamptz`：proxy 写入用 aware UTC（正确），后端写入走 `server_default now()`（正确），绝对时间一致
- 但 SQLAlchemy/asyncpg 把绑定到 timestamptz 参数的 naive datetime 按 **UTC** 解释 → Shanghai 墙钟被当成 UTC
- 后果：本月/本周窗口的实际起点比预期**晚 8 小时**，月初/周初 0:00-8:00 之间的事件被漏计

**修复建议**：按业务时区计算边界后转 aware UTC：

```python
from datetime import datetime, timedelta, timezone
from zoneinfo import ZoneInfo

_TZ = ZoneInfo("Asia/Shanghai")

def _cutoff_for(dimension: str) -> datetime | None:
    now = datetime.now(_TZ)
    if dimension == "month":
        local = now.replace(day=1, hour=0, minute=0, second=0, microsecond=0)
    elif dimension == "week":
        monday = now - timedelta(days=now.weekday())
        local = monday.replace(hour=0, minute=0, second=0, microsecond=0)
    else:
        return None
    return local.astimezone(timezone.utc)  # aware，绑定参数按 UTC 正确解释
```

**验证用例**：造一条 `created_at` 在本月 1 号 0:00-8:00（Asia/Shanghai）之间的事件，确认 month 维度计入。
