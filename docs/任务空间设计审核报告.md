## 三、问题清单

### P1-a（高）seq 并发方案里有一个必然翻车的选项

§3.3 写"（`SELECT max(seq)+1 ... FOR UPDATE` 或 per-mission 计数行，选实现简单者）"。

**`FOR UPDATE` 加在聚合查询上是无效锁**：锁的是行不是间隙，两个并发事务可以都读到同一个 max、各自 +1、插入时撞 `(mission_id, seq)` 唯一索引。T2 验收判据恰好是"并发 100 次写事件无 seq 冲突"——按文档字面二选一，选错就直接挂自己写的验收。

**修复**：设计文档不应把错误选项留给执行者抽签，明确单一方案——per-mission 计数行 `UPDATE ... RETURNING`（天然串行化同一 Mission 的事件写入），或依赖 `(mission_id, seq)` 唯一索引冲突重试。

### P1-b（高）org 级配置没有落库位置，"5+1 表"计数对不上

§3 标题"5 张新表 + 1 张配置表"，正文只列出 5 张（Mission / MissionNode / MissionEvent / MissionArtifact / CapabilityTag）：

- 若 CapabilityTag 就是那张"配置表"，则新表只有 4 张，标题计数错
- 若"+1"指 org 级 mission 配置表，则它整段缺失

而 D6 明确"产物 TTL org 可配 0-365"、§3.1 说 `artifact_ttl_days`"空=取 org 配置，org 配置空=默认 14"——这个 org 配置存在哪里、长什么字段，全文没有答案。执行者到 T1 建表时必然卡住或自行发明。

**修复**：补第 6 张表规格（org 级：artifact_ttl_days、escalation 默认规则等），或明确挂靠现有 org 机制（仓库有 `205b103775c4_add_organization_feature_overrides` 迁移先例可评估复用）。

### P1-c（高）调度器协程方案与生产 K8s 双副本部署冲突

§6 写"backend lifespan 启动的常驻协程（单 worker 前提下安全）"。但 `deploy/k8s/backend.yaml` 是 `replicas: 2`（注释明确"生产至少 2 副本保证高可用"）。两个副本各起一个调度器协程 = 同一节点双重派发、事件重复写入、状态机互相竞争。Compose（P1 验收目标）单副本不受影响，但按现状实施后只能停留在 Compose，上不了仓库自己的 K8s 生产。

**修复**：把部署前提改成机制保证，写进 §6——派发动作走 DB 级 CAS 抢占（`UPDATE mission_nodes SET status='dispatched', ... WHERE id=? AND status='matched'`，抢不到的副本自然退出），或 per-mission PostgreSQL advisory lock。（本条吸收并取代原 P3-3"单 worker 隐式约束"。）

### P1-d（高）匹配器主数据源在当前生态里不存在（数据冷启动缺口）

§5 能力来源主路径 = `Gene.manifest` 的 `capabilities` 字段，回退 `Gene.name`。核实结果：

- backend 里唯一的 `capabilities` 属于 external_agent 子系统（`app/schemas/external_agent.py`），Gene 体系没有任何代码定义、读取、填充该字段
- 种子基因模板（`app/data/gene_templates/`）manifest 无结构化 capabilities，仅 description 文案中出现该词
- GeneHub 推送脚本（`scripts/`）同样不携带

后果：匹配器 v1 实际退化为基因名称字符串相似度，词表标签基本匹配不上，capability_gap 误报一片。这不是代码 bug 而是数据运营缺口，但直接决定演示效果。

**修复**：T1-T4 之间插入一项任务——种子基因补 capabilities 标注并与词表对齐（含 `scripts/upload_seeds_to_genehub.py` 推送同步，遵循"模板与推送同步"规则）。

### P2-a（中）`response_format=json_object` 全链路无先例、未验证

- backend 全库无 `response_format` 使用（编排器是第一个）
- llm-proxy 代码里搜不到对 `response_format` 的任何处理——是否原样透传给上游（尤其 Gemini 转换路径）未验证
- `jsonschema` 不在 backend pyproject 依赖中，需新增

设计自带服务端校验 + 失败重试 1 次的兜底是对的，但 T3 动工前应先做一次 proxy 透传验证，否则"输出强制 JSON Schema"的"强制"是假设不是事实。

### P2-b（中）PG Enum 与全仓库模型惯例冲突

app/models 目录 grep 不到任何 `Enum(` 使用：现有状态字段一律 String + 值域约定（`Gene.visibility`、`WorkspaceTask.status` 皆然）。设计引入 6+ 个原生枚举（mission_status / node_status / mission_event_type / actor_type / 两个 visibility / kind / retention），代价：

- alembic autogenerate 对 PG enum 类型的创建/删除易踩坑
- 后续加枚举值要 `ALTER TYPE`（不能在事务内回滚），与"容器启动自动迁移"的部署方式相性差
- 与仓库既有惯例不一致，两套风格并存

**修复**：降级为 String + 模块级常量词表（Python 侧可用 `Literal` 约束），与 §3.7 事件类型这种开放词表也更匹配。

### P3（低）

1. **token 口径引用失准**：WorkspaceTask 实际字段是 `token_cost / prompt_token_cost / completion_token_cost`（且无 cached 维度）；`token_input/output/cached` 命名的真实先例是 `llm_usage_log`。字段名二选一对齐，避免"口径同现有 WorkspaceTask"误导实现
2. **visibility=`context` 语义悬空**：§3.3 定义"仅注入上下文"，但全文没有任何地方规定上下文如何组装注入——§7.1 任务包只有 upstream_artifacts，没有 context 组装规则。P1 该枚举值无消费者，建议删掉（留 timeline/both）或补注入规格
3. **调度器生命周期**：部署前提问题已升级为 P1-c；剩余部分——复用 heartbeat_scanner 的启停/善后模式（`app/main.py` 已有"后端重启会杀死 asyncio.create_task 管道"的真实坑注释），调度器要处理重启后 dispatched 节点的超时接管
4. **文档位置与命名**："CE 仓库不建 `docs/` 目录"限制已从 CLAUDE.md 移除（2026-08-29），CE `docs/` 目录合法；仅剩"设计文档存 `ee/docs/`"一句与设计文档实际放 CE `docs/` 的归属待明确；文档通篇用旧名 NoDeskClaw，现产品名 DeskClaw（曾用名 NoDeskClaw）

### P4（提示，不阻塞）

- 20MB base64 走 WS 隧道：解码峰值约 27MB 内存 + 插件 `SEND_BUFFER_MAX` 背压丢弃风险，P1 可接受，值得在 §7.2 注一句
- Artifact 清理协程"物理删除存储对象"是对"数据删除一律软删除"规则的显式例外（行级软删 + `artifact_expired` 事件留痕，设计上说得通），建议文档标注这是有意为之
- 节点簿记时间字段（dispatched_at / acked_at 等）文档表格未写时区，实现时注意与 BaseModel 一律 `DateTime(timezone=True)` 对齐（结合技能市场统计 P3 的 naive datetime 教训）

## 五、方案评估（决策质量与产品风险）

### 5.1 决策评价（择要）

| 决策 | 评价 |
|---|---|
| D2 无状态后端编排器，不设专职协调者 Agent | 对。避免一套新的状态管理/成本/故障模式；一次 LLM 调用 + schema 约束是务实选择 |
| D3 roster-blind 拆解 + 独立匹配器 | 全方案最亮的一条：拆解结果不随花名册变动、匹配纯确定性零 token、capability_gap 信号本身就是产品价值（告诉组织缺什么能力该补什么基因） |
| D4 三级上报，L1 带假设继续 | 自主性与阻塞之间的正确默认；所有阻塞都走人类会把产品做死 |
| D6 轻任务 + TTL 隔离区 + 保留转正 | 仪式感成本控制得好，可逆 |
| D8 复用隧道 + 版本协商降级 | 增量上线不强迫换镜像，工程成熟 |
| D9 实例串行 FIFO | 最简单正确的 P1 选择；存在队头阻塞（长节点挡同实例其他 Mission）与新 Mission 饥饿，P2 必改 |

### 5.2 产品级风险（P1 可接受，需有预期）

1. **拆解质量是第一产品风险**：一次 LLM 拆解无迭代，DAG 粒度/依赖质量早期平庸；人工确认是兜底，replan 纯手动。演示前必须用典型需求调过 `ORCHESTRATOR_PROMPT_V1`，别拿默认 prompt 上场
2. **节点间上下文传递单薄**：只有 upstream_artifacts 文件，没有上游结论文交接，"分析→写作"类链条明显吃亏（`visibility=context` 悬空见 P3-2）
3. **预算无硬顶**：仅统计 + L2 预警，DAG 失控自循环烧钱无闸（硬阻断在 P2）。建议至少加单 Mission token 保险丝（超阈值自动挂起待确认）
4. **reject 后再执行粒度未定义**：§9 只说 reject → Mission 回 executing，没说哪些节点重跑；节点级有 acceptance_criteria 却无节点级 accept/reject 流，实施时必然要现场拍板
5. 事件表高频写入（heartbeat/progress/tool_trace）无保留策略，P1 量小无碍，P2 归并已在非目标清单

### 5.3 替代方案对比（方向验证）

- vs 扩展 WorkspaceTask：WorkspaceTask 是平面单任务模型，Mission 要 DAG + 匹配 + 事件流；"不改动现有、全新增"的边界选对了
- vs 专职协调者 Agent（D2 已否决）：同意否决——确定性后端编排可调试、可回放、成本可控
- vs 引入工作流引擎（temporal/langgraph 类）：为 5 张表 + 串行调度引入重型依赖不值，P1 手写最小调度器正确

### 5.4 结论

方案成立，可以按它实施。开工前三个前提：① 调度器加 DB 级抢占（或明确声明 Compose-only）；② 种子基因补 capabilities 数据（T1-T4 间插入任务）；③ 演示前调拆解 prompt。

### 7.2 复核新发现

**N1（P2）实例级串行约束（D9）在多副本下失守**：§6 的 CAS 只防"同一节点被两个副本同时派发"，防不了"不同节点被不同副本同时派发到同一实例"——实例队列是各副本的内存结构，副本 A 给实例 X 派了节点 1，副本 B 的内存里不知道，仍会给 X 派节点 2。D9 的"每实例同一时刻只处理一个节点"承诺在 K8s 双副本下被打破（节点状态机本身仍安全，破坏的是串行调度语义）。**修法**：派发 CAS 条件追加实例级占用检查——`UPDATE ... WHERE id=? AND status='matched' AND NOT EXISTS (SELECT 1 FROM mission_nodes WHERE assigned_instance_id=? AND status IN ('dispatched','acked','running'))`；T5 验收补"双副本并发向同实例派不同节点仅一成功"。

**N2（P2）token 保险丝恢复语义缺失，存在确认-再触发死循环**：§6 第 5 步每轮检查 token 总和超阈值即挂起；§9 answer 解除阻塞回 executing——但 token 总和只增不减，恢复后下一轮 5 秒扫描立即再次超限再次挂起，人工确认形同虚设。**修法**：确认时记录豁免语义（如 `fuse_acknowledged_at` 时间戳 + 确认后阈值翻倍，或本次 Mission 豁免到底），写进 §3.5/§6。

**N3（P3）措辞与清点小问题**：① §9 reject"被点名节点置 failed（attempt 重置）重新入调度"——状态机里 failed 无 →pending 迁移定义，应写明"回 pending 重入队"；② MissionOrgConfig 行创建时机未说明（建议注明读写时 upsert）；③ §3 标题"6 张新表"未计 `mission_event_counters`（T1 已写清，仅标题不一致）；④ 文档仍用旧名 NoDeskClaw（产品现名 DeskClaw，cosmetic）。

### 7.3 复核结论

v2 修订质量高，原清单全部吸收到位。N1/N2 是实施第一天就会撞上的语义缺口（多副本串行、保险丝循环），建议补一轮小修后即可进入 T1；N3 随手带上。
